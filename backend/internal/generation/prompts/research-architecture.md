# Architecture evidence and communication method

Use supplied source evidence and research results; these instructions do not authorize executing repository code or imply new reads occurred. During analysis, verify that important obligations have supporting excerpts; during composition, select existing model facts. If evidence is missing, record the exact scope/role gap. Do not pretend generation can complete missing source research.

Reconcile the independent inventory with researched implementation, caller/dispatch/wiring and contract/consumer evidence for important responsibilities, variants and cross-repository handoffs. Documentation establishes documented design; manifests establish declarations; registrations establish registration. None alone proves a working end-to-end feature. Retain excluded/deferred source areas and unsupported discovery formats as coverage limits. Budgets are bounded; a stopping condition must be honest partial coverage, not a file-count claim of completeness.

Repository boundaries express provenance. Architectural hierarchy expresses software system -> runtime units -> cohesive internal components; use only levels the implementation supports. A library/package is not automatically a service, and a runtime unit is not necessarily a Docker container. Agent tasks/tools usually live inside a host responsibility unless evidence proves a separate boundary. Preserve actual central modules, dispatch variants and specialized tools instead of mapping the directory tree or collapsing the core engine.

For important architectural objects preserve responsibility, caller, inputs/outputs/contracts, technology, known execution form and status. For relations distinguish calls, dependencies, data/artifact transfer, ownership and transitions. Keep interaction semantics explicit; unknown does not mean synchronous. Contract labels name the action/protocol/payload rather than vague arrows. Source membership is an ownership relation from repository, never parent_id.

Follow C4 communication principles without claiming a formal viewpoint when scope/level is unsupported. Each diagram has a question, boundary and one abstraction level. Context orients external relationships; containers explains runtime units; components decomposes one meaningful scope. Reuse exact names/IDs and maintain parent-child continuity from system view to focused drilldowns. Explain boundaries in surrounding prose. Show observed and planned structure distinctly through status and claims; do not invent deployments or trust boundaries.

Static structure is separate from execution order. Scenarios explain trigger -> ordered stages -> acceptance/result, preserving material alternatives, conditions and asynchronous semantics in summaries. Agent-based paths distinguish model decisions from deterministic checks and supported repair. Data chapters explain contract meaning; runtime chapters explain placement. The renderer owns coordinates, colors, boundaries, status styling and layout. Return canonical semantics and known typed views, never styling/rendering code.
