# overview
Goal: orient a new reader before code structure; synthesize last, read first.
Question: What is this product, who uses it, what result does it deliver, and where does its responsibility end?
Inputs: canonical purpose/actor/capability objects, main flow outcomes, material variants/limits, external exchanges, intent and implementation evidence.
Investigation: check principal result and boundary; distinguish stated motivation from observed task; group researched capabilities by useful outcome, not class/endpoint names. Account for significant families and their status.
Output: short definition -> actors/outcomes -> important inputs/outputs and external responsibilities -> supported scope/limits -> transition to repositories. Use concise Markdown; optional context diagram with one system and direct external participants.
Evidence/gaps: cite principal assertions. Preserve source conflicts; missing market/user evidence narrows the introduction, not a reason to invent customers or a roadmap. Missing research is not feature absence.
Exclusions: no internal module inventory, technology dump, startup commands, detailed access rules or full scenario. Detailed users/capabilities only get separate chapters when substantial and distinct.
Acceptance: the reader can explain purpose, actors, result and boundary; material variants survive at outcome level; prose and context share canonical identity; overview adds orientation without repeating the passport.
