Create the standard product passport as a v2 authored document over the supplied canonical model. Return Views matching the supplied schema: sections=[], document populated, shared diagrams, and card_theme only as allowed by the supplied branding context. Do not return a separate model or change canonical facts/IDs.

Document contract:
- document: {version: 2, chapters: [...]}
- Chapter: {id, title, question, blocks}. Use allowed semantic category IDs, unique once each, stable titles and the reading order in the category requirements. The five required chapters are overview, repositories, architecture, scenarios, technologies. Do not add legacy Section fields such as status, summary, scenario_ids or checklist to Chapter.
- DocumentBlock fields are kind, markdown, reference_id, object_ids, claim_ids, table_style. Set only the payload for its kind; unused strings/arrays stay empty or omitted as the supplied schema permits.
- kind=markdown: markdown contains safe prose, subheadings, lists, small Markdown tables or source-supported command fences. Attach existing claim_ids to factual paragraphs/table assertions; prefer atomic paragraphs so the inspector has precise support. Nonfactual headings/transitions and explicit unresolved questions may have no claims. Never invent a claim to fill a block.
- kind=diagram_ref: reference_id names an existing diagram in this Views result. All other payload fields, including claim_ids, are empty/omitted; the diagram's canonical objects/relations carry claims.
- kind=scenario_ref: reference_id names an existing canonical scenario; use only in scenarios. All other payload fields, including claim_ids, are empty/omitted; scenario steps carry claims.
- kind=object_table: object_ids select existing canonical objects, claim_ids support the selected facts, table_style is objects, repositories or technologies. Repositories style contains repository objects; technologies style contains attributed objects with known technology. Keep markdown/reference_id empty.

Plan the whole reading journey before writing; compose detailed chapters from canonical facts and synthesize overview last, then return it first. Begin each chapter with a short answer to its question. Order prose, tables and typed references freely to explain the actual product. Before/after each diagram, explain its scope, main distinction or important contract and transition to the next view. Avoid a fixed stack of repeated widgets.

Placement:
- overview: purpose, actors, outcomes, inputs/outputs, boundary, supported limits; optional product-context view. No internal inventory or full flow.
- repositories: one row per supplied repository, source ownership and named cross-repository handoffs. Repository-only diagrams; a single repository usually needs no graph.
- architecture: whole-system structure, then focused views of important complex subsystems. Preserve actual modules/tools/contracts/status; exclude repository objects. One scope and abstraction level per view, with parent-child continuity.
- scenarios: representative ordered scenario_ref blocks plus a concise cited Markdown matrix accounting for material variants, shared/distinct stages, implementation status and completion/acceptance differences. Do not emit a full scenario per parameter combination.
- technologies: the full object_table with table_style=technologies, ordered consistently with architecture, plus concise role/scope/version caveats. No diagrams or scenarios.
- Supporting chapters follow their category questions; users/capabilities normally integrate into overview and domain into data. Omit optional chapters that would only repeat content or list generic missing information. Required chapters with gaps state exactly what remains unverified.

Shared diagram contract: id, title, kind, summary, node_ids, relation_ids, and optional question/scope_object_id. Allowed kinds: repositories, context, containers, components, domain, data, deployment, states. Give every diagram a clear question and scope; scope_object_id identifies a non-repository object whose immediate architectural children are shown. A containers scope is a software_system. Omit scope_object_id on repositories diagrams. Select only existing objects/relations, and include both endpoints of each selected relation. Repositories diagrams contain only repositories; all other diagrams exclude them. Context shows one product boundary and direct external participants; containers shows runtime-unit structure; components shows one subsystem's internals. Do not skip architectural levels within scope or mix parents and descendants as peers; relevant external supporting boundaries may appear at their own level. Keep names/IDs consistent. Use focused views, usually 5-10 nodes each, and enough drilldowns to preserve an important engine. This is a readability guide, not a global model/diagram cap.

Static arrows show actual contracts/interactions, never execution numbering. Scenario steps express ordered behavior. Deployment requires environment evidence; domain/data/states views require corresponding supported relations. No coordinates, HTML, CSS, JavaScript, SVG, Mermaid, generated imports, executable MDX, external embeds or unsafe links.

Give every full diagram_ref and scenario_ref one home; never repeat them across chapters. Do not repeat their whole content in Markdown. Brief references and shared object identities connect the story. Keep source URLs, line anchors and opaque internal IDs in evidence metadata, except useful source navigation/command paths in Development. Do not invent product facts, commands, owners, rationale, deployment state or successful checks. If needed model support is absent, preserve the precise gap rather than fabricating new facts during composition.
